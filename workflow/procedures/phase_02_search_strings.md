# Phase 2 — Search Strings

## Objective and rationale

Design reproducible, database-aware search strategies from the approved concept map. Query families must reflect the research question rather than a fixed universal taxonomy.

## Required inputs

- `01_search/SEARCH_CONCEPTS.md` and `01_search/KEYWORD_MATRIX.csv`.
- Approved scope, subquestions and source plans.

## Research operations

1. Select query families needed for this protocol, such as broad discovery, specific subquestions, named periods, source genres or methods.
2. Combine concept blocks with documented Boolean, phrase, truncation and proximity choices.
3. Produce database-specific translations only for identified target systems.
4. Plan pilot checks for sentinel concepts and obvious false positives.
5. Document filters, date coverage and the intended role of every query.

## Expected artifacts

- `01_search/SEARCH_STRINGS.md`

## Evidence and provenance requirements

Preserve exact planned strings, target database, syntax version if known, filters and derivation from concept IDs. Execution belongs to Phase 3.

## Academic judgment points

Balance recall and precision; decide when heterogeneous subquestions require separate queries; avoid method filters that would erase eligible evidence.

## Uncertainty and failure handling

Label untested syntax and unavailable database documentation. Record proposed alternatives without claiming they work.

## Prohibited actions

Do not claim result counts, fabricate platform syntax, or require Core/Outcome/Mechanism/Boundary/Method query families for every topic.

## Completion requirements

Every planned query has a purpose, traceable concept logic, target context and explicit limitations ready for human review.
